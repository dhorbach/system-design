    Building a distributed job scheduler

    Problem

    A distributed job scheduler runs code at a chosen time, either once (“send this email at 09:00 tomorrow”) or on a repeating cron schedule (“rebuild the report every hour”), across many machines, so no single crash loses or delays work. Many teams or tenants share the one platform, so none of them has to run and babysit timers of their own.

    The features fit in one sentence. The hard part is the guarantees around them, which the non-functional requirements spell out.

    Requirements

    Each ID reappears as a tag wherever the design implements that requirement.

    Functional requirements

    • One-off and recurring jobs. Run a job once at a chosen time, or repeatedly on a cron schedule evaluated in the job’s own time zone. Cron runs are created one at a time, each computed from the previous scheduled time, so a crash never breaks the series (job store).
    • Create, cancel and query. Clients manage jobs through an API and can see the state of every run. Cancellation is lazy: a cancelled run simply fails its conditional update when its time comes (timing wheel).
    • Per-job policies. Each job carries its own priority, retry limit, timeout and misfire policy. They are copied onto each run when it is created, so a later edit cannot change a run that was already planned (job store).
    • Retries and a dead-letter queue. Failed runs retry with backoff; runs that use up their attempts are kept for inspection and manual retry. Dead runs are kept for a fixed window, for example 14 days, and a manual retry reuses the same run id (correctness).
    • Many tenants. One platform is shared by many teams or tenants. Every job carries a tenant id, which drives fair claiming, concurrency caps and each tenant’s dead-letter queue (behaviour under load).

    Non-functional requirements

    • Accepted means it will run. Once the API says “scheduled”, the job runs even if machines crash. The job store is the single source of truth that every other component rebuilds from, and an outbox plus a sweeper close the gap between database and queue (job store, dispatch queue and workers).
    • Fire on time. Scheduling lag (actual start minus intended start) stays small, usually under a second for urgent work. Runs are loaded about 30 seconds ahead and fired from memory; the worst-case delay after a scheduler crash is the lease TTL, typically 10–30 s (scheduler, timing wheel).
    • Run at least once, and make duplicates harmless. Crashes cause retries, so the design makes repeats safe. Writes are fenced on epoch and attempt, and every run carries an idempotency key (correctness).
    • Survive peaks. People schedule on round times. Most of a day’s load can land on second :00 of each hour. A platform averaging 40 runs per second can face 30,000 in that one second, so priority and misfire policies are applied where runs are created, not only at the queue (behaviour under load).
    • Stay fair. One tenant’s huge batch or broken endpoint must not starve everyone else. Per-tenant queues or weighted fair claiming, plus concurrency caps per tenant and per destination endpoint (behaviour under load).

    Out of scope

    • Exactly-once execution. It is not achievable over a network; the design delivers at-least-once and makes repeats safe instead.
    • Partitions and leases at small scale. Below a few thousand dispatches per second the design at lower scale is enough.

    Traffic

    every-minute: 2,000 × 1,440 = 2,880,000 runs/day
    hourly: 20,000 × 24 = 480,000 runs/day
    daily: 100,000 × 1 = 100,000 runs/day
    total: 3,460,000 runs/day ÷ 86,400 s ≈ 40 runs/s

    The 2,000 every-minute jobs are under 2% of the definitions but produce over 80% of the runs.

    The peak

    At 09:00:00 every every-minute job, every hourly job and the 09:00 share of the daily jobs are due in the same second:

    2,000 + 20,000 + (8% × 100,000 = 8,000) = 30,000 runs in one second
    30,000 ÷ 40 = 750 × the average

    An ordinary top of the hour is 22,000 runs, and every top of the minute is 2,000. Between those instants the system is almost idle.

    Storage

    3,460,000 runs/day × 1 KB ≈ 3.5 GB/day
    3.5 GB/day × 30 days ≈ 100 GB in the hot table

    Job definitions are negligible next to that: 122,000 rows. Partitioning runs by day and dropping old partitions keeps the hot table at this size; the job store section covers how at full detail.

    Worker concurrency

    average: 40 runs/s × 2 s = 80 calls in flight
    peak: 30,000 runs × 2 s = 60,000 call-seconds of work
    cleared in 10 s: 60,000 ÷ 10 = 6,000 calls in flight
    cleared in 60 s: 60,000 ÷ 60 = 1,000 calls in flight

    The calls are outbound HTTP, so this is mostly waiting on the network. The real limit is how many concurrent calls the tenants’ endpoints can take, which is why concurrency caps per tenant and per endpoint are a requirement.

    Database writes

    One run costs about five writes over its life: create, dispatch (with its outbox row), claim, result, and the outbox delete.

    average: 40 runs/s × 5 = 200 writes/s
    peak: 30,000 runs × 4 writes after creation = 120,000 writes
    spread over 10 s: 12,000 writes/s

    The runs for 09:00 already exist as pending rows, so creation is not part of the burst. Batching the dispatch updates is what makes the rest fit.

    Scheduler and memory

    polling: 256 partitions × 1 query/s = 256 queries/s, whatever the job count
    buffer, typical: 30 s lookahead × 40 runs/s = 1,200 runs in memory
    buffer, before 09:00: 30,000 runs × about 200 bytes ≈ 6 MB

    At this size a min-heap or the language’s built-in timers are enough; a timing wheel pays off at much larger timer counts.

    What the numbers say

    • Size for the peak, not the average. 40 runs per second fits on one modest database. 30,000 in one second is far beyond the few thousand dispatches per second that the design at lower scale handles.
    • Put a buffer between deciding and doing. The scheduler can mark 30,000 runs due in a second; workers need 10 to 60 seconds to run them. The dispatch queue absorbs the difference.
    • Decide who waits. If the burst takes 10 seconds to clear, some runs are 10 seconds late. Priority and fairness decide which ones.
    • Storage is not the hard part. About 100 GB of hot data needs retention, not sharding.

    High-level design

    The design separates three concerns (storing what should run, deciding when it is due, and running it) so each part scales and fails independently.

    The life of one run

    1. CreatedA client calls the API: “call this URL every day at 09:00”. The API stores a job definition and the first run, pending, due tomorrow at 09:00.
    2. LoadedAbout 30 seconds before 09:00, the scheduler node that owns the run’s partition finds it in its regular poll and holds it in memory.
    3. FiredAt 09:00:00 the scheduler marks the run dispatched (a write only the current owner can make) and publishes it to the queue. For a cron job it also creates tomorrow’s run.
    4. ExecutedA worker takes it, marks it running, calls the endpoint and sends heartbeats while it waits.
    5. FinishedSuccess marks it succeeded. Failure schedules a retry with backoff, or marks it dead after the last attempt. If the worker dies, a reaper notices the missing heartbeats and puts the run back to pending.

    The six ideas that make it work

    Partitions with leasesMany scheduler nodes, but each run handled by exactly one Fencing tokensA frozen node waking up and acting on stale ownership In-memory timing wheelFiring at the exact millisecond without querying the database constantly Queue between scheduler and workersSlow jobs never delaying scheduling Retries that are safe to repeatCrashes cause retries; retries must be harmless Peak-aware policiesEveryone schedules at :00

    1API service

    Clients use one small REST API to create jobs, cancel them and read their runs. A request is accepted only once the job and its first run are committed to the job store.

    EndpointWhat it does
    POST /v1/jobsCreate a one-off or cron job
    GET /v1/jobs/{job_id}Read a job definition and its next run time
    PATCH /v1/jobs/{job_id}Edit the schedule, the request or the policies
    DELETE /v1/jobs/{job_id}Cancel a job and its pending runs
    GET /v1/jobs/{job_id}/runsList a job’s runs and their states
    GET /v1/runs?state=deadList the tenant’s dead-letter queue
    POST /v1/runs/{run_id}/retryRetry a dead run

    A one-off job sends "run_at": "2026-11-17T09:00:00Z" in place of schedule. The body maps one to one onto the jobs table in the job store.

    What each call does

    • Create inserts the job row and its first pending run in one transaction, then answers. The job is durable from the moment that commit succeeds.
    • Edit changes the definition only. Runs already created keep the request and policies they copied, so an edit applies from the next run onward.
    • Cancel stops the job from creating new runs and deletes its pending ones. A run already loaded by a scheduler is not hunted down; its conditional update finds no pending row when it fires.
    • Retry resets the same dead run to pending. It keeps its run id, so the receiver sees the same idempotency key.

    Details that matter

    • Safe retries of create. The client sends its own Idempotency-Key header on POST /v1/jobs, so a create that timed out and was sent again does not produce two jobs.
    • Jobs due very soon. A job created inside the scheduler’s 30-second lookahead window is pushed straight to the node that owns its partition, so it does not wait for the next poll.
    • Validation at the door. Reject cron expressions that do not parse, unknown time zones, and request URLs that point at internal addresses. The URL is checked again when the worker connects, because DNS can change in between.
    • Tenancy. The API derives the tenant from the authenticated caller and ignores any tenant named in the body. Every read and write is scoped to it, and create is rate-limited per tenant.
    • Errors. 400 for an invalid schedule or request, 404 for a job or run the tenant does not own, 409 for retrying a run that is not dead, 429 when the tenant is over its rate limit.

    2Job store

    The job store is the single source of truth: every other component can crash and rebuild its state from it.

    It holds two kinds of record, because they behave differently.

    RecordWhat it isHow often it changes
    Job definitionSchedule, payload or HTTP request, retry policy, priority, ownerRarely, when someone edits it
    RunOne execution: run_id, job_id, scheduled_at, state, attempt, partitionConstantly: created, claimed, retried, finished

    A run moves through states: pending → dispatched → running → succeeded, or back to pending for a retry, or to dead when retries run out.

    Design rules

    Copy, don’t reference. When a run is created, copy the request, timeout and retry policy from the definition into the run row. An edit made at 08:59:59 then cannot change the 09:00 run that was already planned.

    Index for “what’s due”. The scheduler’s question is always “which pending runs are due before time T?” Index on (partition, state, next_run_at) so that is a short range scan, not a full table scan.

    Brief: sharding. Splitting one logical table across several database servers, each holding a slice of rows chosen by a key. Here the key is a hash of job_id, so load spreads evenly and one job’s runs stay together.

    Cron runs are created one at a time. When a cron run is dispatched, compute the next fire time from the previous scheduled time (not from now) and insert that run in the same transaction. A crash can then never break the series. Add UNIQUE (job_id, scheduled_at) so a retried insert is a harmless no-op.

    Pick the store by scale. Postgres or MySQL comfortably handles thousands of runs per second and gives you transactions and conditional updates. Beyond that, shard it (Vitess for MySQL, Citus for Postgres), or move to Cassandra or DynamoDB with time-bucketed partition keys. Wide-column stores make conditional updates expensive, so many designs keep the hot run table in SQL and move only finished runs to Cassandra or S3 as history.

    Prune finished runs. Partition runs by day and drop old partitions, or archive finished runs elsewhere. Row-by-row deletes on a busy table are expensive in every database.

    3Scheduler

    The scheduler fires each run at the right time, exactly once per dispatch, even when scheduler machines crash. The difficulty is coordination: every run must be covered by exactly one machine.

    The standard answer has three parts. Partitions split the job space into fixed slices. A lease, a lock that expires unless renewed, gives each slice exactly one owner. Fencing makes the storage reject writes from an owner whose lease has passed to someone else.

    Why the obvious designs fail

    • One scheduler node is a single point of failure, and one machine’s scan speed caps throughput.
    • Every node scans everything. Two nodes find the same due run and both dispatch it.

    Partitions

    Split the job space into a fixed number of partitions, say 256: partition = hash(job_id) % 256. Store the partition on every run row. A partition is the unit of ownership: at any moment exactly one scheduler node is responsible for it.

    Use many more partitions than nodes. Adding or removing a node then just moves some partitions between owners; no job is ever rehashed.

    Leases

    Brief: lease. A lock with an expiry time. The holder must renew it before it expires; if the holder dies, the lease lapses on its own and someone else can take it. Unlike a plain lock, a crashed holder cannot block everyone forever.

    Each partition has a lease record in a coordination service (etcd, ZooKeeper) or a database table: (partition, owner, epoch, expires_at). The owner renews every few seconds. If it crashes, it stops renewing, the lease expires after its TTL (10–30 s is typical) and another node claims it. Every claim increments the epoch. This design keeps leases in a table in the job store, so the epoch check and the state change happen in one SQL statement. With etcd or ZooKeeper, the coordination service becomes one more component to run.

    Brief: etcd and ZooKeeper. Small, strongly consistent key-value stores built on a consensus algorithm (Raft and ZAB respectively). Every node sees the same answer to “who owns partition 17?”, which is exactly what leases need.

    Fencing: why leases alone are not enough

    A node can freeze: a long garbage-collection pause, a network partition, a VM migration. It wakes up still believing it owns partitions that were reassigned while it slept. If it dispatches now, jobs run twice and state gets overwritten.

    Brief: fencing token. A number that increases every time ownership changes hands. Every write carries the number its writer was given; the storage rejects any write carrying a number lower than the current one. The stale owner’s writes simply fail.

    The epoch is the fencing token. The dispatch write checks it:

    UPDATE runs SET state = 'dispatched'
WHERE run_id = ?
  AND state = 'pending'
  AND (SELECT epoch FROM leases WHERE partition = ?) = ?;  -- my epoch

    Zero rows affected means ownership was lost: stop working on that partition. The check must live in the storage write itself; a check done earlier in the scheduler’s own memory is exactly what a frozen node gets wrong.

    The loop each owner runs

    1. Poll ahead. About once a second: SELECT run_id, next_run_at FROM runs WHERE partition = ? AND state = 'pending' AND next_run_at <= now() + 30s. One query per partition per second, however many jobs.
    2. Buffer in memory in a timing wheel or min-heap keyed by fire time (see the timing wheel). Jobs created through the API inside the window are pushed straight to the owning node.
    3. Fire. When a run’s time comes, do the fenced update above, then publish to the dispatch queue (dispatch queue and workers covers the crash between these two steps).
    4. Reschedule. For cron jobs, insert the next run in the same transaction as the update.

    Failover and rebalancing

    When a node claims a partition, after a crash or a rebalance, it starts the loop from scratch: query the database, fill its in-memory buffer, continue. Nothing is handed over in memory, which is why failover is simple. Runs that came due during the TTL gap fire late but still fire, so the TTL is your worst-case failover delay and the main tuning knob: shorter recovers faster but causes more false expirations during brief network blips.

    When a node joins, existing nodes release partitions down to about total / nodes each: finish in-flight dispatches, delete the lease, and the new owner claims it with a higher epoch. Release a few at a time to avoid every node reloading at once. Kafka’s consumer groups and Temporal’s shard ownership work this way.

    When to skip all of this

    Below a few thousand dispatches per second you can skip partitions and leases entirely. See the design at lower scale: several identical schedulers using SELECT ... FOR UPDATE SKIP LOCKED let the database’s row locks do the coordination.

    Inside the scheduler: the timing wheel

    A timing wheel holds a large number of timers cheaply, so the scheduler can fire each run at its exact moment while querying the database only about once a second.

    The problem

    Each poll returns every run due in the next 30 seconds, possibly thousands, each due at a different millisecond. Something in memory must hold them and hand each back at the right time. Three options:

    OptionInsertFireFits
    One OS timer per jobCheap per timer, costly in totalCallbackUp to tens of thousands of timers
    Min-heap by due timeO(log n)O(log n) popMost schedulers; Go’s runtime timers work this way
    Timing wheelO(1)O(1) per jobHundreds of thousands to millions of timers
    Brief: O(1) and O(log n). Big-O notation describes how cost grows with the number of items n. O(1) means constant cost however many items exist; O(log n) grows slowly (about 20 steps for a million items).

    How it works

    Picture a circular array of N slots, like a clock face. Each slot covers one tick of time, for example 100 ms. A pointer moves one slot forward every tick and wraps around at the end.

    • Insert a job due in d ticks into slot (now + d) mod N.
    • Each tick, fire every job in the slot the pointer lands on.
    • Jobs more than one lap away carry a rounds counter. A job due in 17 ticks on a 12-slot wheel goes 5 slots ahead with rounds = 1. The first time the pointer passes, it decrements the counter; the second time, it fires.

    Hierarchical wheels

    Round counters waste work: a job ten laps out is visited ten times before it fires. Large systems stack wheels like clock hands: a fine wheel for the next second at 10 ms per slot, a coarser one for the next minute at 1 s per slot. A job starts in the coarsest wheel that covers its delay, and when its slot comes up it moves down to the next finer wheel instead of firing. Kafka uses this for delayed operations; Netty’s HashedWheelTimer is the single-wheel version; the Linux kernel’s timers use a related design.

    A basic wheel in Go

    A single-level wheel with round counters fits in about 70 lines. It is the same structure as the simulation above.

    package wheel

import (
	"sync"
	"time"
)

type entry struct {
	runID  string
	rounds int // full laps still to wait
}

type Wheel struct {
	mu    sync.Mutex
	slots [][]entry
	cur   int           // slot the pointer is on
	tick  time.Duration // time covered by one slot
	fire  func(runID string)
}

func New(n int, tick time.Duration, fire func(string)) *Wheel {
	return &Wheel{slots: make([][]entry, n), tick: tick, fire: fire}
}

// Add schedules runID to fire after delay. O(1).
func (w *Wheel) Add(runID string, delay time.Duration) {
	d := int(delay / w.tick)
	if d < 1 {
		d = 1 // due now or overdue: fire on the next tick
	}
	w.mu.Lock()
	defer w.mu.Unlock()
	n := len(w.slots)
	slot := (w.cur + d) % n
	w.slots[slot] = append(w.slots[slot], entry{runID, (d - 1) / n})
}

// Run advances the pointer once per tick until stop is closed.
func (w *Wheel) Run(stop <-chan struct{}) {
	t := time.NewTicker(w.tick)
	defer t.Stop()
	for {
		select {
		case <-stop:
			return
		case <-t.C:
			w.advance()
		}
	}
}

func (w *Wheel) advance() {
	w.mu.Lock()
	w.cur = (w.cur + 1) % len(w.slots)
	var due []string
	keep := w.slots[w.cur][:0]
	for _, e := range w.slots[w.cur] {
		if e.rounds == 0 {
			due = append(due, e.runID)
		} else {
			e.rounds--
			keep = append(keep, e)
		}
	}
	w.slots[w.cur] = keep
	w.mu.Unlock()

	for _, id := range due {
		w.fire(id) // outside the lock: fire does I/O
	}
}

    Usage: w := wheel.New(600, 100*time.Millisecond, dispatch) gives a 60-second wheel with 100 ms precision; start it with go w.Run(stop) and call w.Add(runID, time.Until(nextRunAt)) for each run the poll returns.

    What a production version adds:

    • Hand-off on fire. Here fire runs on the ticking goroutine, so a slow dispatch delays the next tick. Send the id to a channel or worker pool instead.
    • Catching up. A Go ticker drops ticks when the receiver falls behind. Compute how many ticks have elapsed from the clock and advance that many slots.
    • The scheduler’s bookkeeping. A set of run ids already in the wheel, and a way to drop every entry of a partition when its lease is lost.

    Using it inside the scheduler

    • Deduplicate across polls. With a 30-second lookahead, each run appears in about 30 consecutive polls. Keep a set of run_ids already in the wheel.
    • Due now or overdue: never the current slot. The pointer has already visited the current slot, so a run placed there waits a whole lap. Fire such a run directly without inserting it, or put it in the next slot and accept up to one tick of delay.
    • Firing means the fenced write, then publish. Zero rows updated means the run was cancelled or the lease was lost: drop it silently.
    • On lease loss, clear that partition’s entries, so a former owner stops firing jobs it no longer owns.
    • Cancel lazily. Don’t search the wheel for a cancelled job; let it fire and fail the conditional update.
    • Crashes lose nothing. The wheel is a cache of the database’s next 30 seconds. A new owner repolls and rebuilds it.

    At moderate scale, tens of thousands of pending jobs, a min-heap or the language’s built-in timers do the same job. The wheel pays off at very large timer counts.

    4Dispatch queue and workers

    The dispatch queue separates deciding when from doing the work, so a slow job can never delay scheduling. Workers pull from it, run the job, and report back to the job store.

    The queue

    Kafka, SQS or RabbitMQ all work. Use separate queues or topics per priority (and for very large tenants) so a bulk backlog cannot hold up urgent work.

    Brief: Kafka offsets and head-of-line blocking. A Kafka consumer records progress as one offset per partition, meaning “everything before here is done”. A job that takes 30 seconds therefore holds back every job behind it in that partition. SQS-style queues acknowledge each message separately and don’t have this problem, which is why many schedulers prefer them for job dispatch.

    Workers

    A worker takes a run, marks it running with its own id, and starts a visibility timeout: a deadline after which the run counts as abandoned. While working it sends heartbeats that push the deadline forward. If the worker dies, heartbeats stop, the deadline passes, and a reaper (a background sweep) puts the run back to pending for another worker.

    The worker’s result write is fenced the same way as the scheduler’s dispatch, using attempt (incremented on every claim) as the token:

    UPDATE runs SET state = 'succeeded'
WHERE run_id = ? AND state = 'running'
  AND worker_id = ? AND attempt = ?;

    If a slow worker’s lease expired and another worker reclaimed the run, the slow worker’s late write affects zero rows and cannot corrupt the newer attempt.

    The crash window between database and queue

    Firing a run touches two systems: the database (mark dispatched) and the queue (publish). No transaction spans both, so a crash between them forces a choice:

    OrderCrash between the stepsResult
    Mark, then publishRun marked dispatched, never queuedSilently lost
    Publish, then markRun queued, still pending in the databaseDispatched twice

    Prefer the duplicate: workers are idempotent anyway (see correctness).

    Better still, use an outbox:

    Brief: transactional outbox. Write the state change and an “outbox” row in one database transaction. A separate relay process reads outbox rows and publishes them to the queue, deleting each after it is acknowledged. The database commit becomes the only decision point, so nothing can be lost; the relay may publish twice, which idempotency absorbs.

    Either way, run a sweeper that finds runs stuck in dispatched with no worker acknowledgement after a timeout and resets them to pending. It catches whatever slips through every other mechanism.

    Correctness: at-least-once, idempotency, retries

    The system promises at-least-once execution and makes duplicates harmless with idempotency. That pair is what people usually mean by “exactly-once”.

    Why exactly-once is impossible

    A worker calls an endpoint and the call times out. Did the endpoint do the work and the reply get lost, or did the request never arrive? The caller cannot know. It must either retry (risking a duplicate) or give up (risking a loss). A scheduler that never loses work has to retry, so duplicates will happen.

    Brief: idempotent. An operation is idempotent if doing it twice has the same effect as doing it once. “Set balance to 100” is idempotent; “add 10 to balance” is not.

    Idempotency keys

    Give every run a unique id and send it on every attempt, for example as an Idempotency-Key header. The receiver stores each key under a UNIQUE constraint in the same transaction as the work. A repeated key returns the stored result without redoing anything. Keep keys for at least as long as a run can still be retried, including manual retries from the dead-letter queue.

    Also send X-Scheduled-At and X-Attempt, so the receiver knows which scheduled run this is and whether it is a retry.

    Retries

    Retry failures with exponential backoff and jitter:

    delay = random(0, min(cap, base × 2attempt − 1))
    Brief: jitter. Random spread added to retry delays. Without it, every job that failed together at 09:00:00 retries together at 09:00:02, 09:00:04 and so on: synchronized waves that hit an already struggling endpoint at once.

    Respect what the endpoint tells you: honour Retry-After on 429 and 503 responses. Decide which failures are worth retrying. Timeouts, connection errors and 5xx usually are; a 400 or 404 usually is not, and retrying it only wastes attempts.

    The dead-letter queue (DLQ)

    After max_attempts, a run moves to dead. The DLQ is simply the dead runs of a tenant, kept for a fixed window (for example 14 days) so people can inspect and retry them. A manual retry resets the same run (same id, so the same idempotency key) rather than creating a new one.

    Poison jobs

    A job that crashes its worker (say, a huge response causing an out-of-memory kill) returns via the reaper and crashes the next worker too. Apply backoff to reaped runs as well, and count crashes against max_attempts, so one bad job cannot take down the fleet.

    Behaviour under load

    A scheduler is judged by its peaks, not its average. People write 0 9 * * *, not 17 9 * * *, so at 09:00:00 the every-minute, hourly and daily jobs all land in the same second.

    A platform averaging 40 runs per second can face 30,000 in that one second. Most real-world failures of schedulers are failures of peak behaviour, so design for these cases explicitly.

    Missed runs: choose a misfire policy

    If the system was down at 03:00, what happens on recovery? Make it a per-job setting:

    PolicyBehaviourGood for
    Coalesce (default)Run once now, skip the restDigests, reports, syncs
    Fire allReplay every missed runBilling, per-period processing
    SkipWait for the next scheduled timeHealth checks, cache warmers

    Without a policy, replaying every missed run of a per-minute job after a two-hour outage fires 120 executions back to back. If the catch-up query is ordered oldest-first, those stale runs also fill every batch ahead of jobs due right now.

    Priority at the source, not only at the queue

    Ordering the queue by priority only helps among runs that already exist. If the scheduler creates runs purely by time, a critical job in the last batch before the peak still waits behind all the batches before it. Apply priority when runs are created and claimed, and pre-create large crons further ahead so the peak is ready before it starts.

    Strict priority starves low-priority work under sustained load. Use weighted claiming (for example 70/20/10 of capacity) or aging, which promotes a run once it passes its lag target.

    Fairness between tenants

    If the ten largest tenants own 40% of all jobs, they own 40% of the 09:00 burst too. Use per-tenant queues or weighted fair claiming, plus concurrency caps per tenant and per destination endpoint, so the scheduler cannot overwhelm the endpoints it is calling.

    Brief: thundering herd. Many clients acting at the same instant (all retrying, all reconnecting, all reloading) and overwhelming a shared resource. Jitter, rate limits and staggered work are the standard defences.

    Failover during a peak

    If workers pre-claim runs before they are due, a worker that dies holding them delays every one of them by its lease length. Keep pre-claiming small and close to the due time, and don’t pre-claim critical runs at all.

    What to measure

    • Scheduling lag (actual dispatch minus intended time), as p50/p99 per priority. This is the single best health signal.
    • Pending backlog per partition and per tenant.
    • Lease churn: claims and expirations per minute. A spike means nodes are flapping.
    • Retry rate, DLQ inflow and reaper resets.
    • Duplicate deliveries, measured on the receiving side via repeated idempotency keys.

    Design at lower scale: let the database coordinate

    Below a few thousand dispatches per second, you can drop partitions, partition leases and even the message broker. The database’s row locks do all the coordination.

    Brief: FOR UPDATE SKIP LOCKED. FOR UPDATE locks the rows a query returns until the transaction ends. SKIP LOCKED makes the query pass over rows another transaction already holds instead of waiting for them. Several workers running the same query at the same moment therefore get disjoint sets of rows. Postgres and MySQL 8 both support it.

    Every worker runs the same short transaction:

    SELECT id FROM runs
WHERE state = 'pending' AND next_run_at <= now()
ORDER BY priority, next_run_at
LIMIT 100
FOR UPDATE SKIP LOCKED;

UPDATE runs SET state = 'running', worker_id = ?, attempt = attempt + 1,
       lease_expires_at = now() + interval '5 minutes'
WHERE id IN (...);
COMMIT;  -- before doing any work

    Commit before calling anything, so row locks last milliseconds. A reaper resets rows whose lease_expires_at has passed. Results are fenced on attempt exactly as in dispatch queue and workers. Because state and queue are the same rows, the crash window between database and queue from component 4 does not exist here.

    The price is that every claim is a query against the same database, so it reaches its limit earlier than a design with a separate queue and needs sharding at a lower volume. One MySQL-specific trap is gap locking: at the default REPEATABLE READ level, a claim query that finds nothing still locks the empty index range and stalls inserts into it. Running claims at READ COMMITTED avoids this.
