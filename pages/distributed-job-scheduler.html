    Building a distributed job scheduler

    Problem

    A distributed job scheduler runs code at a chosen time, either once (“send this email at 09:00 tomorrow”) or on a repeating cron schedule (“rebuild the report every hour”), across many machines, so no single crash loses or delays work. Many teams or tenants share the one platform, so none of them has to run and babysit timers of their own.

    Terminology

    The requirements and guarantees below are stated per job, per run or per attempt, so each of the three words has one meaning throughout the guide.

    TermMeaningExample
    JobWhat a client creates: what to run, when to run it and with which policies. A job does no work itself; it produces runs. Its stored record is the job definition.“Call this URL every day at 09:00”
    RunOne scheduled occurrence of a job: the job at one scheduled time. A run keeps the same id from creation to its final state, however many times it is retried.That job’s run for 09:00 on 17 November
    AttemptOne try at executing a run. Every run that executes has at least one; each retry is a new attempt of the same run.The second call, made after the first timed out

    How they relate

    A tenant owns many jobs. A one-off job produces one run; a cron job produces at most one run per scheduled time. Scheduled times missed during an outage may produce no run, as the misfire policy says, and an edit may replace a run that has not started. A run is executed in one or more attempts, and only the latest attempt may record its result.

    A job set for 09:00 every day produces 30 runs in a 30-day month. If the run on the 12th times out twice and succeeds on the third try, the month still has 30 runs: that one has three attempts and the other 29 have one each, 32 attempts in total.

    Jobs and runs are rows in the job store. An attempt is not a row of its own: it is a counter on the run, raised each time a worker claims it.

    Neighbouring words

    • Execute is what a worker does during one attempt. “Execution” is never used as another word for a run.
    • Fire is the moment the scheduler dispatches a run that has come due. Jobs do not fire; their runs do.
    • Task is only the container that a container job starts on a cluster such as Kubernetes or ECS.
    • Worker and executor name the same process, the one that performs attempts. “Executor” is used where the kind of job matters: the HTTP executor, the container executor.

    Requirements

    Each ID reappears as a tag wherever the design implements that requirement.

    Functional requirements

    • One-off and recurring jobs. Run a job once at a chosen time, or repeatedly on a cron schedule evaluated in the job’s own time zone. A job’s kind can be HTTP or container, and new kinds can be added later. Crashes and restarts never lose or duplicate a scheduled run; runs missed during an outage are handled as the job’s misfire policy says (job store, behaviour under load).
    • Create, cancel and query. Clients manage jobs through an API and can see the state of every run. Cancelling a job stops it from scheduling more runs. Runs already handed to workers are cancelled one by one, and a cancelled run that has not started never starts. Cancelling one run of a cron job leaves the rest of its series running (API service, dispatch queue and workers).
    • Per-job policies. Each job carries its own priority, retry limit, timeout and misfire policy. An edit applies to every run that has not started yet; a run already dispatched or running keeps the settings it started with, and an edit never makes a run fire twice (API service, job store).
    • Retries and a dead-letter queue. Failed runs retry with backoff; runs that use up their attempts are kept for inspection and manual retry. A dead run can be retried for a fixed window, for example 14 days after it died; after that, retry is refused and the row stays queryable until the 30-day retention removes it. The receiver sees a manual retry as the same run, not a new one (correctness).
    • Many tenants. One platform is shared by many teams or tenants. Tenants are isolated: each sees and manages only its own jobs, runs and dead-letter queue, within its own rate limits (API service, behaviour under load).

    Non-functional requirements

    • Accepted means it will run. Once the API says “scheduled”, its runs execute even if machines crash. The one exception is a failover of the job store’s database, which can lose writes acknowledged in roughly the last second before it. No accepted job is lost when any single machine or component fails, except the job store’s primary: its replicas are updated asynchronously, so a failover can lose API writes (creates, edits, cancels, retries) acknowledged in the last second or so before it. Failover never promotes a replica further behind than that, and recovery needs no manual intervention (surviving a database failure, dispatch queue and workers).
    • Fire on time. Scheduling lag (the time a worker starts the run minus its intended time) stays within a target per priority, even at the peak: p99 under 2 s for critical and high, under 30 s for normal, under 5 minutes for low. When a scheduler node crashes, the runs it owned may start late by a bounded amount, the lease TTL plus about one claim interval and one poll (typically 15–40 s); every other node’s runs keep their target (scheduler, behaviour under load).
    • Run at least once, and make duplicates harmless. Crashes cause retries, so the design makes repeats safe. Exactly-once execution is not achievable over a network, so the design delivers at-least-once. A run may execute more than once; every attempt carries the same run id, so the receiver can always recognise a repeat, and making a repeat harmless is the receiver’s job. A late result from an old attempt never overwrites a newer one (scheduler, correctness).
    • Survive peaks. People schedule on round times, so one second a day can carry 750 times the average load, and one second every hour about 650 times. A platform averaging 40 runs per second must absorb 30,000 due in one second, with critical and high-priority runs still meeting their lag target (capacity estimates, behaviour under load).
    • Stay fair. One tenant’s huge batch or broken endpoint must not starve everyone else. One tenant’s load, however large, never pushes another tenant’s runs past their lag target, and never exceeds what its destination endpoints were told to expect (behaviour under load).

    Out of scope

    • More than one region. The design runs in one region with one job store; losing the region is a disaster-recovery event, not a failover.
    • Dependencies between jobs. Jobs are independent; workflows (run B after A succeeds) belong to a workflow engine on top.
    • Pausing and resuming a job. A job is active until it is cancelled.
    • Schedules finer than a minute. Cron’s smallest step is one minute; a one-off job can still name any second.
    • Deduplication inside the receiver. The platform sends a stable run id on every attempt; storing it and refusing repeats is the receiver’s job.

    Back-of-the-envelope estimates

    Before choosing components, size the system: how many runs it executes, how unevenly they arrive, how much it stores and how many runs are executing at once. The averages turn out to be small. The worst second is 750 times the average, and that one second drives the design.

    Traffic

    every-minute: 2,000 × 1,440 = 2,880,000 runs/day
    hourly: 20,000 × 24 = 480,000 runs/day
    daily: 100,000 × 1 = 100,000 runs/day
    one-off: 50,000 runs/day
    total: 3,510,000 runs/day ÷ 86,400 s ≈ 40 runs/s
    with 2% retried: about 41 attempts/s

    The 2,000 every-minute jobs are under 2% of the definitions but produce over 80% of the runs.

    The peak

    At 09:00:00 every every-minute job, every hourly job and the 09:00 share of the daily jobs are due in the same second:

    2,000 + 20,000 + (8% × 100,000 = 8,000) = 30,000 runs in one second
    30,000 ÷ 40 = 750 × the average

    An ordinary top of the hour is about 26,000 runs: 2,000 + 20,000, plus about 4,000 of the other 92,000 daily jobs (92,000 ÷ 23 hours). Every top of the minute is 2,000. Between those instants the system is almost idle.

    Storage

    3,510,000 runs/day × 1 KB ≈ 3.5 GB/day
    3.5 GB/day × 30 days ≈ 100 GB in the hot table

    Job definitions are small next to that: 122,000 recurring jobs, plus 50,000 one-off jobs a day that are removed with their runs after 30 days, so about 1.6 million rows. Splitting the runs table into daily table partitions and dropping old ones keeps the hot table at this size; the job store section covers how at full detail.

    Worker concurrency

    average: 40 runs/s × 2 s = 80 calls in flight
    peak: 30,000 runs × 2 s = 60,000 call-seconds of work
    cleared in 10 s: 60,000 ÷ 10 = 6,000 calls in flight
    cleared in 60 s: 60,000 ÷ 60 = 1,000 calls in flight

    The calls are outbound HTTP, so this is mostly waiting on the network. The real limit is how many concurrent calls the tenants’ endpoints can take, which is why concurrency caps per tenant and per endpoint are a requirement. Container jobs change the picture: they run for minutes rather than seconds and are limited by cluster CPU and memory rather than by endpoints, so they need their own concurrency budget.

    Per-tenant defaults follow from the same numbers. A default cap of 5% of the peak capacity, 300 concurrent attempts, lets one tenant use a twentieth of the fleet in the worst second; a default of 50 concurrent calls per destination endpoint protects receivers that never planned for the burst. A tenant that needs more asks for a raise (behaviour under load).

    Database writes

    A clean run costs six row writes: its insert (made when the previous run of its job is dispatched), the dispatch update and its outbox row, the outbox delete, the claim and the result. Three land in the firing second; the other three follow as the relay publishes and workers drain the queue.

    scheduler, in the firing second: 30,000 runs × 3 = 90,000 row writes
    relay and workers, over 10 to 60 s: 30,000 × 3 = 90,000 row writes = 1,500 to 9,000 writes/s
    average day: 41 attempts/s × 6 ≈ 250 writes/s

    The firing second is the number to size for: 90,000 row writes in one second is far more than one database primary takes.

    Shards and batches for the firing second

    One Postgres or MySQL primary comfortably sustains roughly 5,000 to 10,000 small single-row commits per second, and several times that many rows when they are batched. Two choices make the firing second fit. Shard the job store by partition, for example 16 shards with Citus or Vitess, so each shard takes about 5,600 row writes in that second. And batch each scheduler’s dispatches into one transaction per partition per tick, which turns those rows into a few hundred commits per shard. If a shard still falls behind, dispatch drains over two or three seconds in priority order (scheduler), so critical and high-priority runs go first and keep their lag target. The queue does not remove any of these writes; it spreads the claims and results over the 10 to 60 seconds that workers take to drain the burst.

    Writes that are not runs

    heartbeats, peak: 6,000 attempts in flight ÷ 5 s interval = 1,200 writes/s
    heartbeats, average: 80 ÷ 5 s = 16 writes/s
    lease renewals: 256 partitions ÷ 5 s ≈ 50 writes/s, whatever the load
    retries: 2% of attempts repeat 5 writes: about 5 writes/s on average, 3,000 in the minute after the peak

    Heartbeats are the largest of these at the peak, and container jobs, which heartbeat for minutes, dominate them; keep the interval at a few seconds, not below one.

    Scheduler and memory

    polling: 256 partitions × 1 query/s = 256 queries/s, whatever the job count
    buffer, typical: 30 s lookahead × 40 runs/s = 1,200 runs in memory
    buffer, before 09:00: 30,000 runs × about 200 bytes ≈ 6 MB

    At this size a min-heap or the language’s built-in timers are enough; a timing wheel pays off at much larger timer counts.

    What the numbers say

    • Size for the peak, not the average. 40 runs per second fits on one modest database. 30,000 in one second is far beyond the roughly 2,000 runs per second that one database handles even in the design at lower scale.
    • Put a buffer between deciding and doing. The scheduler can mark 30,000 runs due in a second; workers need 10 to 60 seconds to run them. The dispatch queue absorbs the difference.
    • Decide who waits. If the burst takes 10 seconds to clear, some runs are 10 seconds late. Priority and fairness decide which ones.
    • Storage is not the hard part; the write burst is. About 100 GB of hot data needs only retention, but the 90,000 row writes of the firing second need batching and a sharded job store.

    High-level design

    The design separates three concerns (storing what should run, deciding when it is due, and running it) so each part scales and fails independently.

    The life of one run

    1. CreatedA client calls the API: “call this URL every day at 09:00”. The API stores a job definition and the first run, pending, due tomorrow at 09:00.
    2. LoadedAbout 30 seconds before 09:00, the scheduler node that owns the run’s partition finds it in its regular poll and holds it in memory.
    3. FiredAt 09:00:00 the scheduler marks the run dispatched and hands it to the queue; for a cron job it also creates the next run. The mark is a write only the current owner can make, and the hand-off is an outbox row written in the same transaction, which a relay then publishes to the queue.
    4. ExecutedA worker takes it, marks it running, does the work (calls the endpoint, or starts the container) and sends heartbeats while it waits.
    5. FinishedSuccess marks it succeeded. Failure schedules a retry with backoff, or marks it dead after the last attempt. If the worker dies, a reaper notices the missing heartbeats and treats it the same way.

    The six ideas that make it work

    Partitions with leasesEach run is handled by exactly one of many scheduler nodes Fencing tokensWrites from a node that lost ownership are rejected In-memory timer bufferA timing wheel or heap fires runs on time without querying the database constantly Queue between scheduler and workersSlow runs never delay scheduling Retries that are safe to repeatCrashes cause retries, and every retry is harmless Peak-aware policiesThe :00 burst is absorbed without starving urgent runs

    1API service

    Clients use one small REST API to create jobs, cancel them and read their runs. A request is accepted only once the job and its first run are committed to the job store.

    EndpointWhat it does
    POST /v1/jobsCreate a one-off or cron job
    GET /v1/jobs/{job_id}Read a job definition and its next run time
    PATCH /v1/jobs/{job_id}Edit the schedule, the job spec or the policies
    DELETE /v1/jobs/{job_id}Cancel a job: no more runs are scheduled
    GET /v1/jobs/{job_id}/runsList a job’s runs and their states
    GET /v1/runs?state=deadList the tenant’s dead-letter queue
    POST /v1/runs/{run_id}/retryRetry a dead run
    POST /v1/runs/{run_id}/cancelCancel one run that has not finished

    What each call does

    • Create answers only after the job and its first run are committed together, so an accepted job is durable.
    • Edit changes the schedule, spec or policies. The next run that has not started is replaced to match; runs already started keep the settings they began with.
    • Cancel a job stops it scheduling more runs. Runs not yet started are cancelled; runs already executing finish but are not retried.
    • Cancel a run stops one run that has not finished. For a cron job, the rest of the series carries on.
    • Retry sends a dead run back to pending under the same run id, so the receiver sees the same idempotency key.

    Creating a job

    POST /v1/jobs

201 Created
{ "job_id": "j_7f3a", "next_run_at": "2026-11-17T08:00:00Z" }

    A one-off job sends "run_at": "2026-11-17T09:00:00Z" in place of schedule. kind chooses which executor runs the job, and spec holds that kind’s settings, including its timeout; a container job sends "kind": "container" with an image, command and resource limits instead (example in the job store). Each body field maps to a column of the jobs table; the idempotency key arrives as a header. backoff_base and backoff_cap are optional and default to 2 s and 5 minutes. next_run_at in the response is not stored on the job: it is the scheduled_at of the job’s pending run that has not been attempted.

    How each call works in the store

    • Create inserts the job row and its first pending run in one transaction, then answers. The job is durable from the moment that commit succeeds.
    • Edit changes the definition and replaces the job’s next run in the same transaction: the pending run that has not been attempted yet (attempt = 0) moves to cancelled with cancel_reason = 'replaced_by_edit', and a new one is inserted from the new schedule. The uniqueness rule on (job_id, scheduled_at) leaves cancelled rows out, so when only the spec or policies change, the replacement takes the same scheduled time without a conflict. Every edit also raises the job’s version. Runs copy it, and a first attempt is dispatched only while its version still matches the job, so a run planned under the old schedule can never fire next to the new one. Runs that have already started, including those waiting to retry, keep the spec and policies they copied and are not affected.
    • Cancel a job sets the job’s status to cancelled, raises its version, and moves its pending runs to the cancelled state (cancel_reason = 'job_cancelled'), in one transaction. The rows stay, so the job and its history remain queryable. A run already loaded by a scheduler is not hunted down; its conditional update finds no pending row when it fires. Runs already dispatched or running continue, but they create no next run, and a failure moves them to cancelled with last_error kept instead of retrying them. Both checks sit inside the writes themselves (the dispatch write and the worker’s failure write), so a cancel that commits mid-transaction cannot slip past them.
    • Cancel a run moves a pending or dispatched run straight to cancelled with a conditional update (WHERE state IN ('pending', 'dispatched')), setting cancelled_at and cancel_reason = 'client', so a worker that later receives it from the queue finds that its claim matches no rows. If it was the pending run of an active cron job, the same transaction inserts its successor, computed from its scheduled time, so cancelling one run never ends the series. A running run gets cancel_requested_at; its worker sees that on the next heartbeat, stops the container or abandons the HTTP call (which may already have taken effect), and records cancelled with its fenced result write.
    • Retry resets the same dead run to pending. It keeps its run id, so the receiver sees the same idempotency key. It does not reset attempt: it raises the run’s attempt limit by the job’s max_attempts, so the retry gets a fresh budget while attempt keeps counting up (dispatch queue and workers explains why the counter must never go back). It also adds one to manual_retries, sets last_retried_at, and records attempts_before_retry = attempt, so backoff starts again from its base. Retry is refused if the job has been cancelled, or once the run has been dead for longer than the 14-day window.

    Details that matter

    • Safe retries of create. The client sends its own Idempotency-Key header on POST /v1/jobs, so a create that timed out and was sent again does not produce two jobs. When the header is present, the API derives job_id from a hash of (tenant_id, idempotency_key), so a repeat maps to the same job id, the same partition and the same shard. The key is stored on the job under UNIQUE (tenant_id, idempotency_key), which therefore only ever has to be checked on one shard; a repeated create hits the constraint and returns the job created the first time.
    • Runs due very soon. A job created inside the scheduler’s 30-second lookahead window is pushed straight to the node that owns its partition, so its first run does not wait for the next poll.
    • Validation at the door. Reject cron expressions that do not parse, unknown time zones, and specs that fail their kind’s schema. Each kind adds its own checks: an HTTP URL must not point at internal addresses (checked again when the worker connects, because DNS can change in between); a container image must come from the tenant’s allowed registries, with CPU and memory inside its quota.
    • Tenancy. The API derives the tenant from the authenticated caller and ignores any tenant named in the body. Every read and write is scoped to it, and create is rate-limited per tenant.
    • Errors. 400 for an invalid schedule or spec, 404 for a job or run the tenant does not own, 409 for retrying a run that is not dead, whose job is cancelled or whose 14-day window has passed, or cancelling a run that has already finished, 429 when the tenant is over its rate limit.

    2Job store

    The job store is the single source of truth: every other component can crash and rebuild its state from it.

    It holds two kinds of record, because they behave differently.

    RecordWhat it isHow often it changes
    Job definitionSchedule or one-off time, what to run (kind and spec), retry policy, priority, ownerRarely, when someone edits it
    RunOne scheduled occurrence of a job: run_id, job_id, scheduled_at, state, attempt, partition_idConstantly: created, claimed, retried, finished

    A run moves through states: pending → dispatched → running → succeeded, or back to pending for a retry, or to dead when retries run out. A run cancelled before it finishes moves to cancelled. A run passed over by the skip misfire policy moves to skipped, and a dispatched run that no worker claims in time goes back to pending through the sweeper.

    Design rules

    Copy, don’t reference. When a run is created, copy the spec, timeout and retry policy from the definition into the run row, along with priority, misfire policy and the job’s version. An edit made while the 09:00 run is executing then cannot change that run, and the version lets the dispatch write reject a run planned before the edit.

    Index for “what’s due”. The scheduler’s question is always “which pending runs are due before time T?” Index on (partition_id, state, next_attempt_at) so that is a short range scan, not a full table scan.

    Shard by partition. The firing second’s 90,000 row writes are more than one primary takes (capacity estimates), so the job store is sharded, and the shard key is the scheduler partition: a partition’s jobs, runs, lease and outbox rows all live on one shard. Every transaction in this design then stays on one shard, and each of the 256 partitions belongs to exactly one of, say, 16 shards.

    Brief: sharding. Splitting one logical table across several database servers, each holding a slice of rows chosen by a key. Here the key is the partition, itself a hash of job_id, so load spreads evenly and one job’s runs stay together.

    Cron runs are created one at a time. When a cron run is dispatched, compute the next fire time from the previous scheduled time (not from now) and insert that run in the same transaction; the dispatch write itself checks that the job is still active. The dispatch and the insert commit together or not at all, so a crash can delay the series but never break it. Cancelling a pending cron run inserts its successor the same way (API service). Add UNIQUE (job_id, scheduled_at), leaving cancelled rows out, so a retried insert is a harmless no-op.

    Misfires. When the run being dispatched is overdue by more than a threshold (for example 60 s), the scheduler applies its copied misfire_policy. Fire all dispatches it and computes the next time from its scheduled time, as above, so every missed time gets its run in turn. Coalesce dispatches it once and computes the next time from now, so the missed times in between never get a run. Skip does not dispatch it: it moves it to skipped and computes the next time from now.

    Daylight-saving changes. A cron time is evaluated in the job’s own time zone. A local time that does not exist (02:30 on the spring change) runs at the next valid instant, 03:00; a local time that occurs twice (on the autumn change) runs once, at its first occurrence. scheduled_at is stored in UTC, so the unique index sees one value either way.

    Checking the series. Creating runs one at a time has one weak point: if anything ever leaves an active cron job with no pending run (a bug, a manual fix in the database, a path nobody thought of), nothing would create the next one. So the owner of each partition also runs a slow check, every few minutes, of one invariant: every active cron job has exactly one pending run that has not been attempted. A job without one gets its next run inserted from now, as its misfire policy says, and the repair is counted. The count should stay at zero; an alert fires when it does not, because a repair means some path broke the chain.

    SELECT j.job_id FROM jobs j                     -- series check
WHERE j.partition_id = ? AND j.status = 'active'
  AND j.schedule IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM runs r
                  WHERE r.job_id = j.job_id
                    AND r.state = 'pending' AND r.attempt = 0);

    Pick the store by scale. One Postgres or MySQL primary comfortably sustains roughly 5,000 to 10,000 small writes per second and gives you transactions and conditional updates. At six writes per run that is about 1,000 to 1,500 runs per second in this design, or 2,000 to 3,000 at three writes per run in the design at lower scale. Beyond that, shard it (Vitess for MySQL, Citus for Postgres), or move to Cassandra or DynamoDB with time-bucketed partition keys. Cassandra makes conditional updates expensive (each is a Paxos round); DynamoDB supports them cheaply per item, but not across items without its transactions. So many designs keep the hot run table in SQL and move only finished runs to Cassandra or S3 as history.

    Prune finished runs. Split the runs table into daily table partitions and drop old ones, or archive finished runs elsewhere; finished one-off jobs go with their runs. Row-by-row deletes on a busy table are expensive in every database.

    Surviving a database failure

    Every guarantee on this page rests on the job store’s commits, so the store’s own failover decides what a database failure can lose. Each shard runs a primary and replicas with automatic failover (Patroni, Orchestrator, or the cloud provider’s). The options differ in when a commit counts as done:

    OptionA commit is acknowledged whenLost on failoverCost
    Asynchronous replication (this design)The primary has written itThe last moments of commits (bounded to about a second here): accepted jobs, dispatches, resultsNothing extra; the usual default
    Quorum commitThe primary and at least one of two or more replicas have it (Postgres ANY 1 (r1, r2), MySQL semi-sync)NothingAbout 1–2 ms per commit within a region; one slow replica does not stall commits
    Managed quorum storageThe storage layer holds it in several zones (Aurora, AlloyDB, Cloud SQL HA)NothingNo replicas to run yourself; tied to one provider

    This design uses asynchronous replication. It is the usual default, costs nothing per commit, and a database failover is rare. The price is a loss window, which NFR1 states: writes acknowledged in roughly the last second before the primary died may be gone. Keep the window bounded: failover refuses to promote a replica that lags by more than about a second (Patroni’s maximum_lag_on_failover, or the equivalent elsewhere), and replication lag is watched like any other health signal.

    What a lost write means, by kind:

    • A create, edit, cancel or retry. The client was told it succeeded and it did not. This is the loss NFR1 accepts. A client that sends its create again with the same idempotency key after a failover gets the job back safely; edits and cancels can simply be repeated.
    • A dispatch, with its outbox row and the next cron run. They were one transaction, so they vanish together and the run is pending again. It is dispatched a second time, and the receiver sees the same run id.
    • A claim, heartbeat or result. The run falls back to an earlier state and runs again; idempotency absorbs the repeat.
    • A lease claim or a run claim. The dangerous kind: a fencing counter that moves backwards could be handed out twice. The failover hook below prevents it.

    Moving to quorum commit later changes nothing else in the design: the same failover simply loses nothing, and NFR1 drops its exception.

    Counters never move backwards

    With asynchronous replication, a lease claim at epoch 8 can vanish with the old primary, and the next claim hands out 8 again, which is exactly what fencing must never allow; a lost run claim does the same to attempt. So the new primary is promoted with writes blocked, and a failover hook raises every counter by a margin far larger than a second’s worth of increments before writes are let through:

    UPDATE leases SET epoch = epoch + 1000,                -- failover hook
       owner = NULL, expires_at = now();

UPDATE runs SET attempt = attempt + 1000,
       max_attempts = max_attempts + 1000,
       attempts_before_retry = attempts_before_retry + 1000
WHERE state IN ('pending', 'dispatched', 'running');

    Every lease is expired, so every partition is claimed again with a higher epoch. Every run that is not final moves its attempt counter forward, and its limit and backoff base with it, so the retries left and the backoff are unchanged; only the attempt number the receiver sees jumps. A worker still running an attempt on that shard finds that its next heartbeat matches nothing and stops, and the reaper runs the run again. A failover therefore costs one round of repeats on that shard, and a stale write is never accepted.

    3Scheduler

    The scheduler fires each run at the right time, and each firing is made by exactly one scheduler node, even when scheduler machines crash. The difficulty is coordination: every run must be covered by exactly one machine.

    The standard answer has three parts. Partitions split the job space into fixed slices. A lease, a lock that expires unless renewed, gives each slice exactly one owner. Fencing makes the storage reject writes from an owner whose lease has passed to someone else. Each lease carries a counter, the epoch, raised every time the slice changes owner; the storage rejects writes that carry an older one.

    Why the obvious designs fail

    • One scheduler node is a single point of failure, and one machine’s scan speed caps throughput.
    • Every node scans everything. Two nodes find the same due run and both dispatch it.

    Partitions

    Split the job space into a fixed number of partitions, say 256: partition_id = hash(job_id) % 256. Store it on every run row. (The column is not called partition because that is a reserved word in MySQL.) A partition is the unit of ownership: at any moment exactly one scheduler node is responsible for it.

    Use many more partitions than nodes. Adding or removing a node then just moves some partitions between owners; no job is ever rehashed.

    Leases

    Brief: lease. A lock with an expiry time. The holder must renew it before it expires; if the holder dies, the lease lapses on its own and someone else can take it. Unlike a plain lock, a crashed holder cannot block everyone forever.

    Each partition has a lease record in a coordination service (etcd, ZooKeeper) or a database table: (partition_id, owner, epoch, expires_at). The owner renews every few seconds. If it crashes, it stops renewing, the lease expires after its TTL (10–30 s is typical) and another node claims it. Every claim increments the epoch. This design keeps leases in a table in the job store, so the epoch check and the state change happen in one SQL statement. With etcd or ZooKeeper, the coordination service becomes one more component to run.

    Brief: etcd and ZooKeeper. Small, strongly consistent key-value stores built on a consensus algorithm (Raft and ZAB respectively). Every node sees the same answer to “who owns partition 17?”, which is exactly what leases need.

    Fencing: why leases alone are not enough

    A node can freeze: a long garbage-collection pause, a network partition, a VM migration. It wakes up still believing it owns partitions that were reassigned while it slept. If it dispatches now, runs execute twice and state gets overwritten.

    Brief: fencing token. A number that increases every time ownership changes hands. Every write carries the number its writer was given; the storage rejects any write carrying a number lower than the current one. The stale owner’s writes simply fail.

    The epoch is the fencing token. The dispatch write checks it:

    UPDATE runs SET state = 'dispatched', dispatched_at = now()
WHERE run_id = ?
  AND state = 'pending'
  AND (SELECT epoch FROM leases WHERE partition_id = ?) = ?   -- my epoch
  AND (SELECT status FROM jobs WHERE job_id = runs.job_id) = 'active'
  AND (attempt > 0 OR job_version =
       (SELECT version FROM jobs WHERE job_id = runs.job_id)); -- not replaced by an edit

    Zero rows affected means the run is no longer this node’s to fire. The check must live in the storage write itself; a check done earlier in the scheduler’s own memory is exactly what a frozen node gets wrong. The job’s status is checked in the same statement for the same reason: a cancel that commits while the dispatch transaction runs would not be seen by an earlier read.

    Zero rows alone does not say why, and the reasons need different reactions, so the node reads the lease and the run once. If the epoch moved, the lease is gone: stop working on that partition. If the run is no longer pending, it was cancelled or replaced: drop it. If it is still pending but its job is cancelled or its version is stale (an edit or a cancel raced the insert of this run), move it to cancelled with a guarded update (WHERE run_id = ? AND state = 'pending'), so it does not come back on every poll.

    The loop each owner runs

    1. Poll ahead. About once a second: SELECT run_id, next_attempt_at FROM runs WHERE partition_id = ? AND state = 'pending' AND next_attempt_at <= now() + 30s. One query per partition per second, however many jobs.
    2. Buffer in memory in a timing wheel or min-heap keyed by fire time (see the timing wheel). Runs created through the API inside the window are pushed straight to the owning node.
    3. Fire. When a run’s time comes, do the fenced update above and insert an outbox row in the same transaction. Dispatches due in the same tick are written as one transaction per partition, in priority order, so at the peak critical and high-priority runs commit and reach the queue first. A relay publishes the rows to the dispatch queue (dispatch queue and workers explains why the scheduler does not publish directly).
    4. Reschedule. For cron jobs, insert the next run in the same transaction as the update; the update has already checked that the job is active. The new run copies the job’s current version. If the run was overdue, its misfire policy decides whether it is dispatched and where the next time is counted from (job store).
    5. Look after the partition. The owner also runs the partition’s relay, reaper, sweeper and series check, so they fail over with the lease and never run twice.

    Failover and rebalancing

    Claiming, renewing and releasing a lease

    Two nodes can try to claim the same expired lease at once, and an owner can renew just as another node claims. Each write carries its guard, like every other write on this page:

    UPDATE leases SET owner = ?, epoch = epoch + 1,              -- claim
       expires_at = now() + interval '20 seconds'
WHERE partition_id = ? AND expires_at < now()
RETURNING epoch;

UPDATE leases SET expires_at = now() + interval '20 seconds'  -- renew
WHERE partition_id = ? AND owner = ? AND epoch = ?;

UPDATE leases SET owner = NULL, expires_at = now()            -- release
WHERE partition_id = ? AND owner = ? AND epoch = ?;

    now() is the database’s clock, so expiry is decided in one place, never by comparing two machines’ clocks. Of two simultaneous claims, the row lock lets one through and the other matches no rows. A renew that matches no rows means the lease is gone, and the node stops at once. Lease rows are never deleted, so the epoch only ever goes up.

    Failover and rebalancing

    When a node claims a partition, after a crash or a rebalance, it starts the loop from scratch: query the database, fill its in-memory buffer, continue. Nothing is handed over in memory, which is why failover is simple. Runs that came due during the gap fire late but still fire, in priority order. The worst-case failover delay is the TTL, plus up to one claim interval for another node to notice, plus one poll, and the TTL is the main tuning knob: shorter recovers faster but causes more false expirations during brief network blips.

    When a node joins, existing nodes release partitions down to about total / nodes each: finish in-flight dispatches, release the lease (the statement above), and the new owner claims it with epoch + 1. Release a few at a time to avoid every node reloading at once. Kafka’s consumer-group rebalancing (generation ids) and Temporal’s shard ownership (range ids) follow the same idea: move a few owners at a time and fence the old one.

    When to skip all of this

    Below about 2,000 runs per second you can skip partitions and leases entirely. See the design at lower scale: several identical schedulers using SELECT ... FOR UPDATE SKIP LOCKED let the database’s row locks do the coordination.

    Inside the scheduler: the timing wheel

    A timing wheel holds a large number of timers cheaply, so the scheduler can fire each run within one tick of its due time while querying the database only about once a second. At this page’s size a min-heap also works; the wheel pays off at much larger timer counts.

    The problem

    Each poll returns every run due in the next 30 seconds, possibly thousands, each due at a different millisecond. Something in memory must hold them and hand each back at the right time. Three options:

    OptionInsertFireFits
    One OS timer per runCheap per timer, costly in totalCallbackUp to tens of thousands of timers
    Min-heap by due timeO(log n)O(log n) popMost schedulers; Go’s runtime timers work this way
    Timing wheelO(1)O(1) per runHundreds of thousands to millions of timers
    Brief: O(1) and O(log n). Big-O notation describes how cost grows with the number of items n. O(1) means constant cost however many items exist; O(log n) grows slowly (about 20 steps for a million items).

    How it works

    Picture a circular array of N slots, like a clock face. Each slot covers one tick of time, for example 100 ms. A pointer moves one slot forward every tick and wraps around at the end.

    • Insert a run due in d ticks into slot (now + d) mod N.
    • Each tick, fire every run in the slot the pointer lands on.
    • Runs more than one lap away carry a rounds counter. A run due in 17 ticks on a 12-slot wheel goes 5 slots ahead with rounds = 1. The first time the pointer passes, it decrements the counter; the second time, it fires.

    Hierarchical wheels

    Round counters waste work: a run ten laps out is visited ten times before it fires. Large systems stack wheels like clock hands: a fine wheel for the next second at 10 ms per slot, a coarser one for the next minute at 1 s per slot. A run starts in the coarsest wheel that covers its delay, and when its slot comes up it moves down to the next finer wheel instead of firing. Kafka uses this for delayed operations; Netty’s HashedWheelTimer is the single-wheel version; the Linux kernel’s timers use a related design.

    A basic wheel in Go

    A single-level wheel with round counters fits in about 80 lines. It is the same structure as the simulation above. Add takes the due time, not a delay, and rounds the target tick up, so a run never fires before its time and at most one tick after it.

    package wheel

import (
	"sync"
	"time"
)

type entry struct {
	runID  string
	rounds int // full laps still to wait
}

type Wheel struct {
	mu    sync.Mutex
	slots [][]entry
	cur   int           // slot the pointer is on
	ticks int64         // ticks since start
	start time.Time     // when tick 0 happened
	tick  time.Duration // time covered by one slot
	fire  func(runID string)
}

func New(n int, tick time.Duration, fire func(string)) *Wheel {
	return &Wheel{slots: make([][]entry, n), start: time.Now(), tick: tick, fire: fire}
}

// Add schedules runID on the first tick at or after due. O(1).
func (w *Wheel) Add(runID string, due time.Time) {
	w.mu.Lock()
	defer w.mu.Unlock()
	since := due.Sub(w.start)
	target := int64(since / w.tick) // tick k happens at start + k*tick
	if since%w.tick > 0 {
		target++ // round up, never down: a run must not fire early
	}
	d := int(target - w.ticks)
	if d < 1 {
		d = 1 // due now or overdue: fire on the next tick
	}
	n := len(w.slots)
	slot := (w.cur + d) % n
	w.slots[slot] = append(w.slots[slot], entry{runID, (d - 1) / n})
}

// Run advances the pointer once per tick until stop is closed.
func (w *Wheel) Run(stop <-chan struct{}) {
	t := time.NewTicker(w.tick)
	defer t.Stop()
	for {
		select {
		case <-stop:
			return
		case <-t.C:
			w.advance()
		}
	}
}

func (w *Wheel) advance() {
	w.mu.Lock()
	w.ticks++
	w.cur = (w.cur + 1) % len(w.slots)
	var due []string
	keep := w.slots[w.cur][:0]
	for _, e := range w.slots[w.cur] {
		if e.rounds == 0 {
			due = append(due, e.runID)
		} else {
			e.rounds--
			keep = append(keep, e)
		}
	}
	w.slots[w.cur] = keep
	w.mu.Unlock()

	for _, id := range due {
		w.fire(id) // outside the lock: fire does I/O
	}
}

    Usage: w := wheel.New(600, 100*time.Millisecond, dispatch) gives a 60-second wheel with 100 ms precision; start it with go w.Run(stop) and call w.Add(runID, nextAttemptAt) for each run the poll returns.

    What a production version adds:

    • Hand-off on fire. Here fire runs on the ticking goroutine, so a slow dispatch delays the next tick. Send the id to a channel or worker pool instead.
    • Catching up. A Go ticker drops ticks when the receiver falls behind. Compute how many ticks have elapsed from the clock and advance that many slots.
    • The scheduler’s bookkeeping. A set of run ids already in the wheel, and a way to drop every entry of a partition when its lease is lost.

    Using it inside the scheduler

    • Deduplicate across polls. With a 30-second lookahead, each run appears in about 30 consecutive polls. Keep a set of run_ids already in the wheel.
    • Due now or overdue: never the current slot. The pointer has already visited the current slot, so a run placed there waits a whole lap. Fire such a run directly without inserting it, or put it in the next slot and accept up to one tick of delay.
    • Firing means the fenced write plus an outbox row, in one transaction. Zero rows updated is handled as in the scheduler: stop the partition if the lease moved, otherwise drop the run, or cancel it if it is stale.
    • On lease loss, clear that partition’s entries, so a former owner stops firing runs it no longer owns.
    • Cancel lazily. Don’t search the wheel for a cancelled run; let it fire and fail the conditional update.
    • Crashes lose nothing. The wheel is a cache of the database’s next 30 seconds. A new owner repolls and rebuilds it.

    The same job with a min-heap

    At this page’s size, at most 30,000 runs in memory before 09:00, a min-heap does the same job, and it is what most schedulers use:

    • Structure. One heap per node, ordered by due time (next_attempt_at), plus the same set of run ids already loaded.
    • Insert. Each poll pushes the runs it has not seen yet: O(log n), about 15 steps at 30,000 entries.
    • Fire. One loop looks at the earliest entry and sleeps until its due time, or until an earlier run is pushed (the API’s runs due very soon), which wakes it. On waking it pops every entry that is due and fires them as one batch, written in priority order.
    • Lease loss and cancel. Removing entries from the middle of a heap is costly, so do it lazily: on pop, skip entries whose partition this node no longer owns; cancelled runs fail the fenced write as before.
    • Precision. A heap wakes at the due time itself rather than at the next tick, limited only by the operating system’s timer.

    The cost is O(log n) per insert and pop: at 30,000 entries that is microseconds per run, far below the database write each firing needs. The wheel pays off at hundreds of thousands to millions of timers, or when inserts far outnumber firings.

    A basic heap buffer in Go

    The heap version uses the standard library’s container/heap. Both sketches were checked with tests: a run never fires early, fires within its precision (one tick for the wheel), overdue runs fire at once, and a newly added earlier run wakes the heap’s loop.

    package timers

import (
	"container/heap"
	"sync"
	"time"
)

type item struct {
	runID string
	due   time.Time
}

// minHeap keeps the earliest due time at index 0.
type minHeap []item

func (h minHeap) Len() int           { return len(h) }
func (h minHeap) Less(i, j int) bool { return h[i].due.Before(h[j].due) }
func (h minHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *minHeap) Push(x any)        { *h = append(*h, x.(item)) }
func (h *minHeap) Pop() any {
	old := *h
	it := old[len(old)-1]
	*h = old[:len(old)-1]
	return it
}

type Buffer struct {
	mu   sync.Mutex
	h    minHeap
	wake chan struct{}         // signalled when a new earliest run arrives
	fire func(runIDs []string) // one batch per wake-up
}

func New(fire func([]string)) *Buffer {
	return &Buffer{wake: make(chan struct{}, 1), fire: fire}
}

// Add schedules runID to fire at due. O(log n).
func (b *Buffer) Add(runID string, due time.Time) {
	b.mu.Lock()
	earliest := len(b.h) == 0 || due.Before(b.h[0].due)
	heap.Push(&b.h, item{runID, due})
	b.mu.Unlock()
	if earliest {
		select {
		case b.wake <- struct{}{}: // the loop re-reads the top
		default: // a wake-up is already pending
		}
	}
}

// Run sleeps until the earliest run is due, fires everything due, repeats.
func (b *Buffer) Run(stop <-chan struct{}) {
	for {
		b.mu.Lock()
		now := time.Now()
		var due []string
		for len(b.h) > 0 && !b.h[0].due.After(now) {
			due = append(due, heap.Pop(&b.h).(item).runID)
		}
		wait := time.Minute // nothing loaded: the next poll will Add
		if len(b.h) > 0 {
			wait = b.h[0].due.Sub(now)
		}
		b.mu.Unlock()

		if len(due) > 0 {
			b.fire(due) // outside the lock: fire does I/O
		}
		t := time.NewTimer(wait)
		select {
		case <-stop:
			t.Stop()
			return
		case <-b.wake:
			t.Stop()
		case <-t.C:
		}
	}
}

    Usage: b := timers.New(dispatchBatch), start it with go b.Run(stop), and call b.Add(runID, nextAttemptAt) for each run the poll returns that is not already loaded.

    4Dispatch queue and workers

    The dispatch queue separates deciding when from doing the work, so a slow run can never delay scheduling. Workers pull runs from it, execute them, and report back to the job store.

    The scheduler records the dispatch and a message to send in one database transaction, so a crash can delay a run but never lose it.

    The queue

    Kafka, SQS or RabbitMQ all work. Use separate queues or topics per priority (and for very large tenants) so a bulk backlog cannot hold up urgent work, and per job kind so each executor pulls only what it can run.

    Brief: Kafka offsets and head-of-line blocking. A consumer in a classic Kafka consumer group records progress as one offset per partition, meaning “everything before here is done”. A run that takes 30 seconds therefore holds back every run behind it in that partition. Kafka’s newer share groups and SQS-style queues acknowledge each message separately and don’t have this problem, which is why many schedulers prefer them for job dispatch.

    The crash window between database and queue

    Firing a run touches two systems: the database (mark dispatched) and the queue (publish). No transaction spans both, so a naive design must choose what a crash between them does:

    OrderCrash between the stepsResult
    Mark, then publishRun marked dispatched, never queuedSilently lost
    Publish, then markRun queued, still pending in the databaseDispatched twice

    If you must choose, prefer the duplicate: receivers can recognise a repeat (see correctness). This design avoids the choice with an outbox:

    Brief: transactional outbox. Write the state change and an “outbox” row in one database transaction. A separate relay process reads outbox rows and publishes them to the queue, deleting each after it is acknowledged. The database commit becomes the only decision point, so nothing can be lost; the relay may publish twice, which idempotency absorbs.

    Who runs the relay, reaper and sweeper. The scheduler node that holds a partition’s lease runs all three for that partition, so they fail over with the lease and never run twice. The relay is woken by each dispatch commit and also polls every 100 ms, so it adds at most about 100 ms to dispatch, and it publishes high-priority rows first. If it stops, nothing reaches the workers, so alert on the age of the oldest outbox row. The sweeper finds runs left in dispatched with no claim for 10 minutes and resets them to pending, to be dispatched again. That timeout sits well above the worst queue wait at the peak (60 s) and the time a run may wait for its tenant’s quota, so it never re-dispatches a healthy backlog. It catches whatever slips through every other mechanism.

    Workers

    A worker takes a run, marks it running with its own id, and starts a visibility timeout: a deadline, stored in heartbeat_deadline, after which the run counts as abandoned. It is a hold on one run, not a partition lease. While working the worker sends heartbeats that push the deadline forward. If the worker dies, heartbeats stop, the deadline passes, and a reaper (a background sweep) puts the run back to pending after a backoff, or to dead when its attempts are used up.

    Each claim raises the run’s attempt counter, and every later write by that worker names the value it got. Once another worker claims the run the number has moved on, so a late write matches nothing.

    Workers are executors, one pool per job kind. The HTTP executor makes the call; the container executor starts the task on a cluster such as Kubernetes or ECS and watches it until it exits. The scheduler, leases, fencing and outbox never look inside the spec. A new kind needs an executor, a validation schema, a queue and a concurrency budget; nothing in scheduling changes.

    Guarding every worker write

    Workers and the reaper race each other just as scheduler nodes do, and the queue may deliver the same run twice. Every write they make carries its guard in the WHERE clause. The guard is attempt: the claim raises it, and every later write names the value its writer got.

    Brief: monotonic fencing token. A number that only ever goes up. Each claim raises attempt by one, and the claiming worker remembers the new value. Its later writes all say WHERE attempt = <my value>, so once anyone else claims the run the number has moved on and the old worker’s writes match no rows. This works only if no value is ever handed out twice. If a manual retry reset attempt to 0, the next claims would reuse 1, 2 and 3, and a worker still holding 3 from before the reset could overwrite the new attempt 3. That is why retry raises the attempt limit instead of resetting the counter.

    In the statements below, job_active stands for (SELECT status FROM jobs WHERE job_id = runs.job_id) = 'active'.

    UPDATE runs SET state = 'running', worker_id = ?,           -- claim
       attempt = attempt + 1, started_at = now(),
       heartbeat_deadline = now() + interval '30 seconds'
WHERE run_id = ? AND state = 'dispatched'
RETURNING attempt;

UPDATE runs SET heartbeat_deadline = now() + interval '30 seconds'   -- heartbeat
WHERE run_id = ? AND state = 'running' AND attempt = ?
RETURNING cancel_requested_at;

UPDATE runs SET state = 'succeeded', finished_at = now()   -- result: success
WHERE run_id = ? AND state = 'running'
  AND worker_id = ? AND attempt = ?;

UPDATE runs SET worker_id = NULL, finished_at = now(),     -- result: failure
       last_error = ?, next_attempt_at = now() + ?,        -- ? = backoff
       state = CASE
         WHEN cancel_requested_at IS NOT NULL OR NOT job_active THEN 'cancelled'
         WHEN attempt >= max_attempts THEN 'dead'
         ELSE 'pending' END
WHERE run_id = ? AND state = 'running'
  AND worker_id = ? AND attempt = ?;

UPDATE runs SET worker_id = NULL, finished_at = now(),     -- reaper
       last_error = 'worker lost', next_attempt_at = now() + ?,
       state = CASE
         WHEN cancel_requested_at IS NOT NULL OR NOT job_active THEN 'cancelled'
         WHEN attempt >= max_attempts THEN 'dead'
         ELSE 'pending' END
WHERE run_id = ? AND state = 'running' AND attempt = ?
  AND heartbeat_deadline < now();

UPDATE runs SET state = 'pending', dispatched_at = NULL    -- sweeper
WHERE run_id = ? AND state = 'dispatched'
  AND dispatched_at < now() - interval '10 minutes';

    A claim that matches no rows means another worker already has the run, or it was cancelled: drop the message. A heartbeat that matches no rows means this worker lost the run: stop. A worker that stops for a cancel records it with the failure write, which turns it into cancelled. The reaper ends a lost attempt exactly as a failure would: cancelled if a cancel was requested or the job is no longer active, dead if the attempts are used up, otherwise pending after a backoff, so a run that kills its worker cannot loop for ever. It names the attempt it saw expire, so a heartbeat that lands first makes the reset match nothing. If a slow worker’s visibility timeout passed and another worker reclaimed the run, the slow worker’s late write affects zero rows and cannot corrupt the newer attempt. When a one-off job’s run reaches a final state, the same transaction sets the job to completed. RETURNING is Postgres syntax; in MySQL, read the row back in the same transaction.

    Container jobs

    • Long runs. A container task can run for many minutes, so set the visibility timeout (heartbeat_deadline) from the heartbeat interval (for example three missed heartbeats), not from the job’s timeout. Otherwise a dead executor holds the run until the full timeout passes.
    • Identity. Pass the run id, attempt and scheduled time as environment variables (RUN_ID, ATTEMPT, SCHEDULED_AT), the container’s equivalent of the idempotency headers.
    • Cancel stops the task. An HTTP call already in flight cannot be recalled, but a container can. When a running run is cancelled, the executor sees cancel_requested_at on its next heartbeat and stops the container.
    • Capacity. Concurrency is bounded by cluster CPU and memory, so per-tenant quotas are in resources, not just in runs.

    Correctness: at-least-once, idempotency, retries

    The system promises at-least-once execution and makes duplicates harmless with idempotency. That pair is what people usually mean by “exactly-once”.

    Why exactly-once is impossible

    A worker calls an endpoint and the call times out. Did the endpoint do the work and the reply get lost, or did the request never arrive? The caller cannot know. It must either retry (risking a duplicate) or give up (risking a loss). A scheduler that never loses work has to retry, so duplicates will happen.

    Brief: idempotent. An operation is idempotent if doing it twice has the same effect as doing it once. “Set balance to 100” is idempotent; “add 10 to balance” is not.

    Idempotency keys

    Give every run a unique id and send it on every attempt, for example as an Idempotency-Key header for an HTTP job or a RUN_ID environment variable for a container. The receiver stores each key under a UNIQUE constraint in the same transaction as the work. A repeated key returns the stored result without redoing anything. Keep keys for at least as long as a run can still be retried, including manual retries from the dead-letter queue.

    Also send the scheduled time and the attempt number (X-Scheduled-At and X-Attempt headers, or SCHEDULED_AT and ATTEMPT variables), so the receiver knows which scheduled run this is and whether it is a retry.

    Retries

    Retry failures with exponential backoff and jitter:

    delay = random(0, min(cap, base × 2n − 1)), where n = attempt − attempts_before_retry

    n counts attempts since the last manual retry, so a retried run starts again from the base delay instead of at the cap.

    Brief: jitter. Random spread added to retry delays. Without it, every run that failed together at 09:00:00 retries together at 09:00:02, 09:00:06 and so on: synchronized waves that hit an already struggling endpoint at once.

    For HTTP jobs, respect what the endpoint tells you: honour Retry-After on 429 and 503 responses. Decide which failures are worth retrying. Timeouts, connection errors and 5xx usually are; a 400 or 404 usually is not, and retrying it only wastes attempts.

    The dead-letter queue (DLQ)

    After max_attempts, a run moves to dead. The DLQ is simply the dead runs of a tenant, kept for a fixed window (for example 14 days) so people can inspect and retry them; after the window, retry answers 409, and the row goes when its daily table partition is dropped at 30 days. A manual retry resets the same run (same id, so the same idempotency key) rather than creating a new one.

    Poison jobs

    A poison job is one whose runs crash the worker itself (say, a huge response causing an out-of-memory kill). Such a run returns via the reaper and crashes the next worker too. The reaper therefore applies backoff to reaped runs and counts each crash against max_attempts, moving the run to dead when they are used up (dispatch queue and workers), so one bad job cannot take down the fleet.

    Behaviour under load

    A scheduler is judged by its peaks, not its average. People write 0 9 * * *, not 17 9 * * *, so at 09:00:00 the runs of the every-minute, hourly and daily jobs all fall due in the same second.

    A platform averaging 40 runs per second can face 30,000 in that one second. Most real-world failures of schedulers are failures of peak behaviour, so design for these cases explicitly. Three per-job and per-tenant rules decide who waits: a misfire policy for runs missed in an outage, priority applied where runs are dispatched and claimed, and caps that keep one tenant from taking the whole peak.

    Missed runs: choose a misfire policy

    If the system was down at 03:00, what happens on recovery? Make it a per-job setting, applied by the scheduler when it dispatches an overdue run (job store):

    PolicyBehaviourGood for
    Coalesce (default)Run once now, skip the restDigests, reports, syncs
    Fire allReplay every missed runBilling, per-period processing
    SkipWait for the next scheduled timeHealth checks, cache warmers

    Without a policy, replaying every missed run of a per-minute job after a two-hour outage fires 120 runs back to back. If the catch-up query is ordered oldest-first, those stale runs also fill every batch ahead of runs due right now.

    Priority at the source, not only at the queue

    Ordering the queue by priority only helps among runs that have already reached it. At the peak the scheduler is the first queue: 30,000 runs fall due in one second, and if it dispatched them in arrival order, a critical run at the back of the batch would wait behind all the rest. So priority applies at each step: within a tick the scheduler writes its dispatch batches in priority order, the relay publishes high-priority outbox rows first, each priority has its own queue, and workers claim from the higher queues first. The runs for 09:00 already exist as pending rows long before the peak, because each was created when its predecessor was dispatched.

    Strict priority starves low-priority work under sustained load. Use weighted claiming (for example 70/20/10 of capacity) or aging, which promotes a run once it passes its lag target.

    Fairness between tenants

    If the ten largest tenants own 40% of all jobs, they own 40% of the 09:00 burst too. Use per-tenant queues or weighted fair claiming, plus concurrency caps per tenant and per destination endpoint, so the scheduler cannot overwhelm the endpoints it is calling.

    Quotas. Each tenant’s caps live in its tenants row: max_concurrent_runs, per_endpoint_limit and rate_limit. Defaults come from the capacity estimates (300 concurrent attempts, 50 concurrent calls per endpoint) and are raised per tenant on request, the way cloud service limits are, with updated_at recording when. The cap is enforced at the claim: before claiming, a worker takes a slot from the tenant’s counter (a counter row or a Redis semaphore), and gives it back with the result; slots expire with the attempt’s visibility timeout, so a dead worker does not leak them. With no slot free, the worker leaves the run dispatched and the queue redelivers it after a short delay. A tenant with one very chatty job can be allowed more than the default, and fair claiming makes that tenant wait for its own extra work instead of everyone else.

    Brief: thundering herd. Many clients acting at the same instant (all retrying, all reconnecting, all reloading) and overwhelming a shared resource. Jitter, rate limits and staggered work are the standard defences.

    A scheduler node failing at the peak

    Suppose one of 20 scheduler nodes dies at 08:59:59, holding a twentieth of the partitions and about 1,500 of the 30,000 runs due at 09:00:00 in its buffer. Nothing in memory is handed over. Its leases expire after the TTL (say 20 s); other nodes notice at their next claim attempt, a few seconds later, and claim them with higher epochs; each new owner polls, reloads and finds every one of those runs overdue. The affected runs are late by the TTL plus up to one claim interval plus one poll, about 25 s here, so the TTL alone is not the worst case. The new owners fire the overdue runs in priority order. Those 1,500 runs miss the lag target of their priority, which is the bounded delay NFR2 allows for the runs of a failed node; the other 28,500 keep their target. To shrink the window, lower the TTL (at the cost of more false expiries), and have a node that shuts down cleanly release its leases at once.

    What to measure

    • Scheduling lag (actual start minus intended time: started_at − scheduled_at), as p50/p99 per priority. This is the single best health signal.
    • Dispatch lag (dispatched_at − scheduled_at), which tells a slow scheduler from a slow queue or too few workers.
    • Age of the oldest outbox row: a stopped relay shows here first.
    • Pending backlog per partition and per tenant.
    • Lease churn: claims and expirations per minute. A spike means nodes are flapping.
    • Retry rate, DLQ inflow, reaper resets, sweeper resets, and series repairs (which should be zero).
    • Replication lag per shard: it is the size of the loss window a database failover would cause right now.
    • Duplicate deliveries, measured on the receiving side via repeated idempotency keys.

    Design at lower scale: let the database coordinate

    Below about 2,000 runs per second, you can drop partitions, partition leases and even the message broker. The database’s row locks do all the coordination.

    Brief: FOR UPDATE SKIP LOCKED. FOR UPDATE locks the rows a query returns until the transaction ends. SKIP LOCKED makes the query pass over rows another transaction already holds instead of waiting for them. Several workers running the same query at the same moment therefore get disjoint sets of rows. Postgres and MySQL 8 both support it.

    Every worker runs the same short transaction:

    SELECT run_id FROM runs
WHERE state = 'pending' AND next_attempt_at <= now()
ORDER BY priority, next_attempt_at       -- priority is a rank: critical 0 … low 3
LIMIT 100
FOR UPDATE SKIP LOCKED;

UPDATE runs SET state = 'running', worker_id = ?, attempt = attempt + 1,
       started_at = now(), heartbeat_deadline = now() + interval '5 minutes'
WHERE run_id IN (...);
COMMIT;  -- before doing any work

    Commit before calling anything, so row locks last milliseconds. A reaper handles rows whose heartbeat_deadline has passed, as in dispatch queue and workers. Results are fenced on attempt exactly as in dispatch queue and workers. Because state and queue are the same rows, the crash window between database and queue from component 4 does not exist here.

    The price is that every claim is a query against the same database, so it reaches its limit earlier than a design with a separate queue and needs sharding at a lower volume: at three writes per run (create, claim, result), one primary handles about 2,000 to 3,000 runs per second.

    A MySQL isolation trap

    One MySQL-specific trap is gap locking: at the default REPEATABLE READ level, a claim query that finds nothing still locks the empty index range and stalls inserts into it. Running claims at READ COMMITTED avoids this.
